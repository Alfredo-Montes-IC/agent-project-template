# Shared skills and agent setup

## One maintained skill, several clients

Edit shared bundles only under `.agents/skills/<name>/`. Each bundle has a portable `SKILL.md` with `name` and `description` and optional relative references. Start with the general [security-review](../../.agents/skills/security-review/SKILL.md) where security guidance is needed.

Codex, current Antigravity App/CLI/IDE, and Gemini CLI discover `.agents/skills/`. Claude Code discovers `.claude/skills/`; those bundles are generated byte-for-byte from the common source. Run `python3 scripts/sync_skills.py` after changing a shared skill. CI rejects drift; do not edit the generated Claude copy. Plain files avoid Windows symlink requirements. No personal/global skill installation is performed by this template.

| Client | Request the workflow | Check discovery |
|---|---|---|
| Codex | `$security-review` followed by the task, or choose it via `/skills` | Inspect the available skills in your installed client |
| Claude Code | `/security-review` followed by the task | Check its skill/command list; reload skills if needed |
| Antigravity | `/security-review` where supported, or mention it by name | Inspect Customizations / active skills |
| Gemini CLI | Explicitly ask to use `security-review` | `/skills list`, then `/skills reload` if needed |
| GitHub Copilot | Ask it to follow `.github/copilot-instructions.md` and read the relevant shared skill file | Verify repository instruction and skill discovery in the installed surface |
| Grok Build | `/security-review` if listed, or ask for it by name | Inspect `/skills`; verify in the installed version |

The same approach applies to `project-customization`, `adversarial-code-reviewer`, `debugging`, and `verification`. The workflow content is identical; shortcut syntax, models, tools, permissions and approval prompts remain client-specific. Use the hyphenated name, without spaces. For older Antigravity releases that only support `.agent/skills/`, update the client or configure that legacy location separately; do not create a second independently maintained skill. Other Grok products or agents may behave differently; ask them to read `AGENTS.md` and the relevant skill file directly unless discovery is verified. Do not assume subagent capability.

Antigravity does not automatically load nested `AGENTS.md` files below an opened repository root; explicitly route it to the applicable scoped files. Its `.agents/skills.json` has a client-defined manifest format, so this template keeps its separate mirror configuration in `.agents/skill-mirrors.json`. Verify behavior in the installed client rather than assuming configuration loaded.

## Which skill to use

These are shared task workflows, not separate agents that run automatically. An agent can read a skill directly if its client does not discover it. Apply all relevant rows; for example, a database-backed UI change may need migration, accessibility, security, and verification guidance.

| Task or trigger | Shared skill | Expected result |
|---|---|---|
| Initialize a project or change its stack or agent setup | [project-customization](../../.agents/skills/project-customization/SKILL.md) | Adapt instructions and context to confirmed project facts |
| Investigate unexpected behavior or a failing check | [debugging](../../.agents/skills/debugging/SKILL.md) | Reproduction, cause, fix and evidence or an explicit unknown |
| Choose and report checks | [verification](../../.agents/skills/verification/SKILL.md) | Risk-appropriate results and unavailable checks |
| Independently challenge a code change | [adversarial-code-reviewer](../../.agents/skills/adversarial-code-reviewer/SKILL.md) | Findings and disposition for the exact reviewed snapshot |
| Review engineering practices and comments in every code change | [code-standards-review](../../.agents/skills/code-standards-review/SKILL.md) | Evidence of guideline compliance and neutral, actionable feedback |
| Security-sensitive work or a code PR | [security-review](../../.agents/skills/security-review/SKILL.md) | Review applicable trust boundaries; independent review of the complete PR diff before opening or marking it ready |
| Change dependencies, actions, or scanners | [dependency-maintenance](../../.agents/skills/dependency-maintenance/SKILL.md) | Provenance, compatibility, verification and recovery evidence |
| Change stored data, schemas, or persistent state | [data-migration](../../.agents/skills/data-migration/SKILL.md) | Compatibility, rollout and tested recovery plan where applicable |
| Design, implement, or test a user-facing interface | [accessibility-review](../../.agents/skills/accessibility-review/SKILL.md) | Applicable automated and manual checks, barriers and untested areas |
| Plan or investigate an actual release, incident, or recovery | [release-recovery](../../.agents/skills/release-recovery/SKILL.md) | Rollout, health and recovery evidence appropriate to the service |
| Project or change has cost implications | [budget-planning](../../.agents/skills/budget-planning/SKILL.md) | Estimated agent, tool, CI and hosting costs and spending limits |
| Write or create a PR description | [pr-description](../../.agents/skills/pr-description/SKILL.md) | Description in the shared What/Why/Changes format |

## Common way of working

1. Read the shared contract and context map, check Git status and the task branch, then load the applicable scoped instructions and skills. Follow higher-priority user and host instructions, including their tool and delegation permissions.
2. Identify the goal, relevant existing behavior and utilities, ownership, acceptance criteria, and unknowns. Preserve unrelated work; record durable decisions in their owning documents.
3. Implement within scope and run checks appropriate to the change. Distinguish local results, hosted CI, and checks that cannot be run. For client-specific discovery, test the actual installed client and version instead of inferring support from these files.
4. Obtain the independent reviews required by the [review workflow](../workflows/adversarial-review.md), respecting host delegation restrictions. If no independent reviewer is available, leave the gate pending. A role definition or self-review is not independent evidence.
5. Review the final diff and report changed behavior, evidence, remaining risks, and any pending handoff or review. Follow the [Git workflow](../standards/GIT_WORKFLOW.md) for staging, commits, and publishing.

This lifecycle applies to each client; invocation, instruction discovery, available tools, and permissions can differ. A reviewer receives the task and exact snapshot independently and reports findings; the author resolves them and requests re-review when needed. For work split among writers, use the [multi-agent workflow](../workflows/multi-agent.md) only when delegation is permitted.

## Reviewer subagents

The template includes `adversarial-reviewer`, `code-standards-reviewer`, and `security-reviewer` definitions for Codex (`.codex/agents/`), Claude Code (`.claude/agents/`), Gemini CLI (`.gemini/agents/`), and Antigravity (`.agents/agents/`). Grok Build documents Claude Code agent compatibility. For every code change, the coordinating agent requests code standards review alongside the other required reviews. Run them in parallel when the client permits it. The definitions point to shared skills and the review workflow. The coordinator starts the reviews. Verify discovery and tool permissions in the client. If a client lacks the role or delegation, use the shared role prompt in an independent session or report a pending gate.

Use the client's permission settings to restrict reviewers to read-only access where supported. A role prompt alone does not enforce a read-only sandbox. Some roles have read and search tools but no Git shell access. The parent must provide the complete staged or PR diff, revisions, and relevant context, or arrange another independent reviewer who can inspect them. The reviewer must report when it cannot verify the exact snapshot or inspect a changed file. An incomplete review cannot pass the gate.

Conditional `migration-reviewer` and `accessibility-reviewer` definitions use the same client locations for data changes and UI work. Additional portable skills are `dependency-maintenance`, `release-recovery`, `data-migration`, `accessibility-review` and `budget-planning`; invoke them by the same client-specific skill mechanism, or read their `SKILL.md` directly. Budget estimates must include agent reviews/API/tool and hosting usage, not just application compute, and verify current billing terms.

## Initialize every checkout

Requires Git and Python 3.10+. From the root run:

```bash
python3 scripts/bootstrap.py
python3 scripts/verify.py
```

On Windows use `py -3` or `python` instead of `python3` if that is your installed launcher. Hooks work through Git's shell and use the same Python policy scripts. Setup refuses to replace a different effective `core.hooksPath`, including inherited global/system configuration. Repeat bootstrap in each new clone; worktrees using a shared hooksPath must share these policy files.

Start at [AGENTS.md](../../AGENTS.md), inspect Git status and branch, read the [context map](../context/README.md), then the assigned task and scoped instructions. Use the [handoff template](../templates/handoff.template.md) to record actual results and the next action before switching agents.

`CLAUDE.md` imports the shared contract. Gemini's project settings select `AGENTS.md`. Current Antigravity surfaces load the root `AGENTS.md` as an always-on workspace rule. Scoped context below the opened workspace may differ by client; follow the context map rather than assuming identical recursive discovery. Context discovery and skill discovery are separate mechanisms.

## Controls and limitations

For a project that needs a connector or MCP server, follow the [integration and permissions guide](integrations.md) to record access, configure each client, and verify the connection.

The shared contract does not grant tool permissions. Claude has a project-local deny baseline for private environment files and common destructive Git commands; it also denies `.env.example` under the wildcard. Other clients require their own runtime permission policies. Git hooks add tool-independent checks after bootstrap; `--no-verify`, changed Git configuration, native GitHub APIs or another unconfigured clone can bypass them. Only activated server-side rules can reject direct protected-branch updates independently of the client.

The included scanner checks file names and a few high-confidence credential patterns. It is not a comprehensive secret scan, SAST, dependency audit, penetration test or security certification. Add application-specific checks once the project's stack exists. Do not claim the application passed tests while this is an uncustomized template.

## Imported skills and applicability

[pr-description](../../.agents/skills/pr-description/SKILL.md) is imported verbatim from
`pr description writer.md`. Use `/pr-description` in clients with slash invocation,
or `$pr-description` in Codex. Source/destination already given by the user or the
repository's PR flow do not need to be asked again, and repository issue-linking
rules (`Refs #<n>` on `task -> dev`; `Closes #<n>` / `Fixes #<n>` on `dev -> main`
for known governing issues even when `dev` or commit messages omit `#<n>`)
supersede step 5. Its local `PR_DESCRIPTION.md`
draft is ignored by Git. Publishing a PR still follows the user's authorization.
Shared skills and their resources are mirrored identically for Claude by the existing sync script.
