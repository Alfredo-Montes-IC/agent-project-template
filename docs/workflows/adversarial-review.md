# Independent adversarial code review

Every code change must be challenged by a reviewer independent of its author before it is committed or proposed in a PR, including code written by the project owner. This includes executable scripts, configuration and infrastructure changes. During implementation, request a separate adversarial subagent when available and authorized, using whichever agent the developer currently uses; review the exact final staged snapshot before committing. Give it the task and acceptance criteria, base revision, exact proposed diff, relevant instructions, and test evidence. Request read-only behavior and restrict permissions where the host supports it; a persona prompt alone is not a sandbox. Do not ask it to merely endorse the implementation. Respect host permissions and higher-priority instructions.

If the host cannot run an independent subagent, use another independent agent session or a human reviewer. A second prompt to the author in the same session is self-review, not independent review. If none is available, record the gate as pending, explain the limitation, and leave the change uncommitted and the code PR unproposed until an independent review is available. Do not invent a reviewer or result. A human review does not need access to private prompts or transcripts.

The reviewer should actively seek incorrect behavior, missing requirements, regressions, security issues, concurrency and edge cases, and misleading or missing tests. Trace suspect paths and cite file locations and evidence; distinguish confirmed findings from uncertainty. Report severity, impact, and a concrete reproduction or reasoning for each finding, followed by residual risks and checks not run. Report no findings explicitly if applicable.

The author addresses findings, runs relevant checks, and obtains reviewer re-evaluation of fixes and any material subsequent changes. Resolve blocking findings before commit and PR; record disagreements and unresolved issues without claiming a pass. Identify the exact staged diff for pre-commit review, and the commit SHA for PR review; repeat the review when the final diff differs materially. In the PR, record reviewer identity or session, independence, reviewed revision, findings and disposition, and result. The same person or agent cannot approve their own work merely by using a different role label.

## Code standards review for every code change

Request the independent `code-standards-reviewer` for the same code change alongside the adversarial reviewer and any applicable specialists. Run reviews in parallel when the client and budget permit. Count the extra review session and any re-review in [budget planning](budget-planning.md) when reviewer usage is metered. Check the final staged snapshot before committing. Before opening or promoting a code PR, confirm the review covers the proposed diff and repeat affected review after material changes. Use the [code standards review skill](../../.agents/skills/code-standards-review/SKILL.md) and record its outcome separately.

If the client lacks the role, give the same brief and snapshot to a separate reviewer session or a human reviewer. If parallel review is unavailable, run the reviews in sequence. A reviewer independent of the author may perform more than one review when separate reviewers are unavailable, with each review explicitly performed and reported. Keep the gate pending when no independent reviewer can perform it.

## Security review before a code PR

Before opening or marking ready any code PR, invoke the portable `security-review` skill in an independent reviewer session and examine the complete PR base-to-head diff in context, even when each commit was reviewed separately. Include the base and head SHAs, task, relevant architecture, existing controls and checks; trace changed trust boundaries and affected paths. Apply the project's actual security policy where relevant. The security reviewer may be the independent adversarial reviewer if it explicitly performs both reviews and reports both outcomes; a separate security reviewer is preferred when practical.

Fix blocking security findings, rerun checks, and re-review affected changes. Re-review when a changed head or base alters the reviewed diff. Record reviewer/session, skill, base, head, findings and disposition, remaining uncertainty, and outcome in the PR. Never claim a pass for an unavailable review. A PR with no executable code, configuration or infrastructure may mark security review not applicable with a reason; if uncertain, request review. A local receipt or green CI cannot prove that security review occurred.

Repository instructions alone cannot enforce independent review. Repository administrators should configure appropriate branch protection or rulesets and required checks or human approvals for the project. Do not assume a CI pass proves an independent review happened.

## Local lock for solo development

Run `python3 scripts/bootstrap.py` once per checkout to install the local hooks. They block direct pushes to `main` and `dev`, and require a matching review receipt before **every commit**, including documentation-only changes. Stage the intended files, then run `python3 scripts/review_gate.py snapshot`. Give the independent reviewer the staged diff, the reported tree and parent, and the task context. After addressing blocking findings, obtain another review of any changed staged snapshot. Only after a completed review, record the review with `python3 scripts/review_gate.py record --tree TREE --parent PARENT --reviewer SESSION --evidence SUMMARY`; use `unborn` as the parent for a new repository. Do not include secrets or private review content. The receipt stays in Git's local metadata, not in the commit. A changed index or parent invalidates it.

Local merge commits are blocked because their additional parents are not covered by this receipt; use the reviewed PR flow for merges. For a new repository, `snapshot` reports a null parent, which is recorded using the literal value `unborn`.

This is a local reminder and workflow lock, not proof of independent review: a user can forge a receipt, alter or bypass hooks, or push from another client. It cannot protect GitHub's web or API paths. An actual server-side lock requires active rules on `dev` and `main` and an independently authenticated reviewer integration that checks the exact PR head and posts a required status. For promotion to `main`, check the final promotion diff and the reviewed changes it contains; invalidate the status when the head changes. Neither a self-reported receipt nor a green generic CI job establishes that review happened. If the independent integration is not configured, report server-side review enforcement as unavailable; do not claim the branch is protected.
