# Dependency and scanner maintenance

The template configures weekly GitHub Actions version updates targeting `dev`, with a `chore/dependabot` branch prefix so generated PRs fit task routing. Verify the first live update PR's branch and checks. Follow the [review workflow](adversarial-review.md) for dependency and action updates.

When adding a package ecosystem, inspect real manifests and lockfiles, add the matching Dependabot entry and directories, and test the actual update workflow. Enable dependency alerts where supported by the repository. Dependabot security-update PRs target the default branch and can conflict with this template's `dev -> main` policy. Reproduce the fix on a reviewed task branch from current `dev`, run checks, integrate and promote normally, then resolve the original alert/PR when the fix reaches `main`. Do not bypass routing or hide an unresolved alert. Review critical advisories promptly rather than waiting for the weekly version schedule.

Verify update provenance, advisories, compatibility, exact action commits and lockfile changes against authoritative sources. Run the affected application checks, then repeat the required PR reviews. Maintain a concrete rollback path. Version-update monitoring is not a vulnerability scan; a zero-alert result does not establish security.

The secret-scanning workflow pins Gitleaks v8.30.1 and the official Linux x64 archive SHA-256. Check its official releases periodically and update the version and checksum together in a reviewed PR; Dependabot does not update this downloaded CLI. The job checks full fetched history and current files using built-in rules, redaction and a config outside the checkout. It does not accept repository ignore files or inline allow comments. A finding requires investigation, revocation/rotation for real credentials and narrow reviewed handling for false positives; do not silence the whole scanner. Raw secret reports must not be uploaded or committed. A workflow itself can be modified in a PR; active rules and independent review remain necessary.

Scanner output is kept in temporary files and removed, because redaction may leave other sensitive values on a matched source line. CI reports a generic failure for either findings or scanner errors. Investigate with the pinned scanner privately, using the same built-in config and scope; never paste raw reports into PRs or upload them as artifacts.

This PR workflow is editable by a branch author, who could replace the scanner job with a successful no-op while keeping its required name. Required-check rules alone do not prevent that. For this solo workflow, independent agent review and preserved CI are the practical controls; tamper-resistant enforcement would require a separately protected workflow or authenticated independent check. Do not claim this template configures that boundary.
